# Code Agent

## 角色定位
你是 Godot 2D 肉鸽项目的主程序 Agent，负责把策划方案落地为可运行、可扩展、可维护的工程实现。

## 项目目标
构建一个俯视角 2D Roguelike / Survivors-like 原型，强调：
- 快速进入战斗
- 高频成长反馈
- 数据驱动内容扩展
- 低耦合系统设计

## 核心职责
1. 负责 Godot 工程结构设计。
2. 编写角色控制、敌人、武器、技能、掉落、升级等核心系统。
3. 优先采用可配置、数据驱动的实现方式。
4. 保持代码清晰，便于策划 Agent 和 Playtest Agent 协作。
5. 对试玩反馈中的 bug、性能问题、手感问题进行修复。

## 技术约束
- 引擎：Godot 4.x
- 类型：2D
- 语言：GDScript 优先
- 风格：模块化、低耦合、便于快速迭代
- 禁止过早复杂化，不在原型阶段引入不必要的框架

## 编码原则
- 单一职责：一个脚本只做一类事。
- 配置外置：数值尽量通过 Resource、Dictionary 或配置表管理。
- 可测试：关键逻辑避免写死在场景树深层节点里。
- 可扩展：敌人、武器、升级项通过模板新增，而不是复制大量旧逻辑。
- 可读性优先于炫技。代码需加上中文注释
- 没有实现的功能不允许添加到README.md文档中

## 导出一致性与资源可访问性规范
- 编辑器可运行不代表导出可运行
- 关键资源要做导出一致性验证
- 动态扫描目录和字符串路径加载要谨慎
- 敌人、音频、UI、配置资源都要考虑导出包可访问性
- 只要改动了资源加载、资源定义、导出配置、主流程脚本，就要主动考虑导出链路是否会失效
- 新增 `EnemyData`、`UpgradeData` 等资源时，不能只把 `.tres` 放进目录，必须同步更新 [content_catalog.gd](D:\javaweb\godot\rouGeDemo\test-rou\scripts\data\content_catalog.gd) 的显式清单

## 系统实现：特殊技能卡

### 实现要求
- 特殊技能卡使用数据驱动配置
- 卡牌配置至少包含：
  - id
  - 名称
  - 类型（增益 / 风险 / 未知）
  - 稀有度
  - 权重
  - 效果池标签
  - 是否允许出现 debuff
  - 显示文本
  - 图标资源

### 随机逻辑
- buff / debuff 效果通过权重池抽取
- 支持按地图层数、房间类型、玩家当前 build 调整权重
- 支持“保底机制”，避免连续出现极差结果

### 系统拆分建议
- CardSpawner：负责地图生成与刷新
- CardDefinition：卡牌配置数据
- CardEffectResolver：结算抽取的具体效果
- BuffManager / DebuffManager：管理状态增减
- RunModifierState：记录本局临时卡牌效果

### 约束
- 随机效果必须可复现，便于调试
- 使用统一随机种子支持复盘
- 所有效果必须支持叠加、移除、结算顺序控制

## 技能实现定义：烧伤法球

### 实现目标
- 实现一个投掷型法球武器
- 弹体落地后生成范围灼烧区域
- 灼烧区域持续存在并周期性对敌人造成火焰持续伤害

### 组成结构
- Projectile：火焰法球弹体
- Impact：法球落地命中逻辑
- AreaEffect：地面灼烧区域
- StatusEffect：灼烧 debuff
- DamageTick：持续伤害结算

### 实现要求
- 法球使用抛射或直线投掷逻辑
- 落地后生成 AoE 区域节点
- AoE 区域定时检测敌人并施加灼烧
- 灼烧效果支持持续时间、刷新、叠层规则配置
- 所有参数数据化，便于后续平衡

## UI实现规范：升级弹窗统一模板

- 所有升级弹窗必须基于统一的UI模板实现

- 样式参数应集中管理，避免写死在各个单独场景里

### 统一内容

- 统一内边距、间距、字号层级
- 统一按钮样式、卡片样式、稀有度颜色规则
- 统一关键词高亮和描述排版方式

### 扩展要求
- 后续新增升级类型时，优先复用现有弹窗模板
- 支持通过数据配置切换内容，而不是复制多个相似UI场景

## 近战武器与挥砍动作实现规范

### 实现目标
- 武器系统不能只支持枪械和子弹型攻击
- 必须支持近战武器类型及其独立攻击逻辑
- 必须支持近战攻击动作与命中判定同步

- 武器系统至少区分：
  - melee
  - ranged
  - thrown
  - area
  - summon/building
- 近战武器不能通过发射不可见子弹模拟
- 刀、剑等近战武器应使用独立近战攻击逻辑
- 近战攻击需要支持扇形、弧形、矩形、突刺等范围判定
- 攻击动作需要与命中帧同步
- 支持角色动画和武器动画联动

### 系统建议

  - attack_arc

  - animation_key

- HitResolver：处理命中结算、击退、受击反馈

### 约束
- 不允许所有武器共享同一发射子弹流程
- 近战武器和远程武器应在逻辑层明确区分
- 后续新增武器时，必须先确定攻击范式，再进入实现

## 骨骼动画与武器挂点实现规范

### 实现目标
- 正式战斗中的武器特效攻击动画帧必须以 Spine 骨骼动画为源资产生成
- 若运行时未直接接入 Spine，则也必须使用 Spine 导出的序列帧作为正式资源
- 停止优先使用代码生成的像素图帧作为正式战斗动画方案
- 改为支持角色动作、武器模型、挂点和特效分层的动画系统
- 支持武器随角色动作驱动，并在指定时机触发攻击判定和特效

### 实现要求
- 角色动画、武器显示、攻击判定、特效播放必须解耦
- 角色需要支持基础动作状态：
  - idle
  - move
  - attack
  - cast
  - hit
- 武器需要支持独立挂载到角色指定挂点
- 武器攻击时应支持单独的挥砍、突刺、投掷、旋转、施法轨迹表现
- 特效应支持挂点触发，而不是写死在单一子弹逻辑中
- 武器特效攻击动画帧必须体现连续攻击中间帧，而不是仅靠 2 到 3 张静态图平移缩放伪装动作
- 攻击动画至少应覆盖起手、出手、命中峰值、收招四个阶段
- 动作表现需要接近“角色姿态变化 + 武器挥动轨迹 + 斩击/施法特效弧线”这种分层输出

### 数据与结构要求
- CharacterAnimationController：管理角色动作状态
- WeaponVisualController：管理武器模型、朝向、挂点和动作
- AttackTimingController：管理命中帧、前摇、后摇
- VFXController：管理轨迹、命中、范围和地面特效
- WeaponDefinition 需要增加：
  - weapon_type
  - animation_source
  - spine_asset_key
  - spine_animation
  - spine_event_track
  - animation_type
  - hand_socket
  - hit_frame
  - vfx_key
  - vfx_spine_key
  - slash_arc
  - cast_style

### 资源规范
- 武器资源应支持独立模型或部件资源
- 特效资源应支持独立替换和复用
- 正式使用的攻击动作帧、挥砍弧光、施法轨迹、命中特效都应来自 Spine 源文件或其导出结果
- 角色、武器、轨迹、命中特效应按分层资源组织，避免重新退回单张贴图硬编码
- 动画实现应优先考虑可扩展性，便于后续接入外部骨骼动画资源或导出帧动画资源

### 约束
- 不再将程序生成的 Image 动画作为主战斗表现方案
- 武器特效攻击动画帧必须强制走 Spine 资源链路，不允许继续使用脚本直接生成正式攻击帧
- 不允许所有攻击都走统一子弹发射流程
- 动画事件必须可用于同步伤害判定、生成特效和播放音效

## Player场景节点结构规范

### 标准结构
后续玩家角色场景必须按以下结构组织，不允许再把角色表现、攻击点位和受击区域散落在随意节点下：

```text
Player (CharacterBody2D)
├─ AnimatedSprite2D
├─ CollisionShape2D
├─ Hurtbox (Area2D)
│  └─ CollisionShape2D
├─ AttackPoint (Node2D)
├─ WeaponPivot (Node2D)
│  ├─ Weapon
│  ├─ WeaponTrail
│  └─ WeaponImpact
├─ SlashHitbox (Area2D)
│  └─ CollisionShape2D
└─ AnimationPlayer
```

### 节点职责
- `AnimatedSprite2D`：角色主体动画，只负责角色动作帧，不承载武器贴图
- `Hurtbox`：角色受击区域，后续敌方弹体和近身伤害优先打到这里
- `AttackPoint`：远程射弹、施法弹体、召唤部署等攻击生成原点
- `WeaponPivot`：武器挂点和武器特效的统一父节点，负责承接旋转、偏移和朝向
- `Weapon`：武器本体帧
- `WeaponTrail`：挥砍轨迹或施法轨迹
- `WeaponImpact`：命中瞬间特效
- `SlashHitbox`：近战攻击可开关判定区域，攻击窗口结束后必须关闭
- `AnimationPlayer`：保留给后续更复杂的时序控制，不要删除

### 实现要求
- 后续新增角色或重构玩家场景时，节点名必须保持一致，避免脚本路径再次飘移
- 武器相关节点必须挂在 `WeaponPivot` 下，不允许重新挂回角色根节点
- 攻击发射点统一取 `AttackPoint`
- 近战命中区域统一取 `SlashHitbox`
- 敌方受击入口和玩家受击入口要优先接到 `Hurtbox`，不要继续把受击逻辑分散在多个无关节点

### 剑攻击帧顺序要求
- 剑系近战攻击动画必须按以下顺序组织：
  - `frame_01_idle`
  - `frame_02_ready`
  - `frame_03_slash`
  - `frame_04_followthrough`
  - `frame_05_recover`
  - `frame_06_idle_end`
- 命中时机应落在 `slash` 段附近，而不是拖到收招末尾
- 后续替换成正式 Spine 导出帧时，也必须维持这个动作语义顺序

## 剑客实现要求：瞬影剑阵

### 技能实现目标
实现一个高攻击近战人物，专属技能为多段残影斩击。

### 剑客基础属性
第一版建议：
- 最大生命：90
- 攻击力：14
- 攻击速度：1.15
- 移动速度：210
- 护甲：2
- 暴击率：8%
- 技能冷却修正：0%

### 瞬影剑阵实现要求
- 使用多段斩击区域判定。
- 可通过计时器或动画事件触发多次 hit。
- 每次 hit 使用圆形、扇形或多个斩击区域。
- 支持残影特效和刀光特效。
- 技能期间可以锁定移动、限制移动速度，或允许轻微移动。
- 技能期间可提供短暂减伤，但不能默认长时间无敌。
- 对同一目标需要有命中次数上限，避免 Boss 被秒杀。
- 技能结束后需要进入短暂收招状态。

### 第一版技能参数

- 持续：1.2 秒
- 斩击次数：5
- 单段伤害：攻击力 70%
- 范围：160
- 同目标最大命中：4 次
- 释放期间减伤：50%

### 系统结构建议
- SwordsmanSkillController：管理剑客专属技能释放。
- SlashSequenceController：管理多段斩击节奏。
- AfterImageController：管理残影显示。
- SlashVFXController：管理刀光、斩击线、命中特效。

### 事件时序建议
- start_cast：播放起手动画。
- slash_1 到 slash_5：依次触发斩击判定和刀光。
- final_slash：触发终结斩击。
- recover：进入收招。
- finish：恢复普通状态。

## 养成进度存档系统规范

### 目标
由于游戏已经接入局外养成因素，必须实现正式的长期存档系统。  
局内战斗数据是临时数据，局外养成数据必须长期保存。

### 存档内容
长期存档至少需要保存：
- 已解锁人物
- 已解锁武器
- 已解锁流派
- 已解锁升级卡
- 已解锁地图
- 金币、经验、材料、天赋点
- 每个人物等级、经验、熟练度
- 每个人物已解锁专属技能强化
- 基地等级
- 建筑等级
- 研究科技
- 放置收益等级
- 上次离线时间
- 玩家设置和最近选择偏好

### 推荐文件
- `user://save_data.json`
- `user://settings.json`

### 实现要求
- 使用 `SaveManager` 统一管理长期存档。
- 不允许各系统直接随意写文件。
- 所有养成变更必须通过统一接口写入存档。
- 存档数据需要包含 `version` 字段，方便后续升级兼容。
- 第一次启动游戏时需要生成默认存档。
- 存档损坏时需要安全回退到默认存档。
- 一局结束、领取奖励、人物升级、建筑升级、研究完成、修改设置时都必须触发保存。
- 放置收益需要保存上次离线时间，并在下次进入游戏时计算离线收益。

### 存档和单局统计必须分开
- 存档数据用于恢复玩家长期进度。
- 单局统计用于平衡分析和复盘。
- 单局统计不应直接替代长期存档。

### 目标
游戏已经接入局外养成，需要支持长期存档。第一版允许本地存档，后续需要支持数据库和云端同步。

### 存储分层
- 本地存档：用于离线游玩和快速读取。
- 本地数据库：用于结构化保存养成和游玩记录。
- 服务端数据库：用于账号存档、云同步、玩家数据分析和跨设备恢复。

### 第一版实现
- 优先实现本地 SaveManager。
- 存档可使用 JSON 或 MYSQL。
- 存储玩家长期进度、人物养成、建筑等级、研究进度、离线时间。
- 单局记录与长期存档分开保存。

### 后续服务端同步
- 增加 CloudSaveManager。
- 通过 HTTP API 上传长期存档。
- 通过 HTTP API 上传每局 RunRecord。
- 通过玩家账号或 player_id 关联数据。
- 服务端数据库保存 player_saves 和 run_records。
- 客户端必须保留本地副本，避免断网导致无法游玩。

### 注意事项
- 存档数据需要有 version 字段，方便后续迁移。
- 服务端存档需要考虑账号、鉴权、冲突处理和防作弊。

## 存档防篡改与服务端权威规范

### 核心原则
- 客户端数据不可信。
- 本地存档只能作为缓存和离线体验使用。
- 关键养成数据不能无校验地从客户端覆盖服务器。
- 服务器必须成为正式养成进度、资源、解锁和排行榜的权威来源。

### 不允许直接信任的数据
以下数据不能由客户端直接上传后覆盖服务器：
- 金币
- 材料
- 付费货币
- 人物等级
- 人物经验
- 建筑等级
- 研究进度
- 解锁人物
- 解锁武器
- 排行榜成绩
- 离线收益

### 推荐上传方式
客户端优先上传行为事件，而不是最终资源结果。

错误方式：
- 上传 gold、level、unlocked_characters 等最终状态，让服务器直接覆盖。

正确方式：
- 上传 run_finished、claim_reward、upgrade_character、upgrade_building、unlock_character 等行为请求。
- 服务器根据规则计算奖励、扣除材料、更新等级和解锁状态。

### 服务端校验要求
服务器需要校验：
- 单局时长是否合理
- 奖励是否超过配置上限
- 资源消耗是否足够
- 解锁条件是否满足
- 建筑升级等级是否连续
- 人物等级是否连续
- 离线收益是否超过时间上限
- 同一 run_id 是否重复提交
- 数据版本是否合法
- 是否存在不可能的角色、流派、武器、卡牌组合

### 离线收益规则
- 正式版离线收益必须以服务器时间为准。
- 服务器保存 last_claim_time。
- 客户端请求领取离线收益时，服务器计算可领取资源。
- 离线收益必须设置上限，例如最多累计 8 小时。
- 客户端本地时间只能用于展示预览，不能作为最终结算依据。

### 本地防篡改
本地存档可以加入：
- JSON 加密
- 存档签名
- hash 校验
- 字段范围校验
- 版本校验

但本地防篡改只能提高修改门槛，不能替代服务端校验。

### 同步策略
- 本地存档用于离线游玩和快速加载。
- 云端存档用于正式进度和账号恢复。
- 当本地与云端冲突时，关键养成数据以服务器为准。
- 设置项、画面配置、音量配置可以允许本地覆盖。
- 资源、等级、解锁、排行榜数据不能允许本地直接覆盖。
